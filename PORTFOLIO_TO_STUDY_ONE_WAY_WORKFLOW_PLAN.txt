===============================================================================
1. USER INTENT
===============================================================================

The Workspace planning sequence must be one-directional and easy to understand:

    Submitted Algorithms
            |
            v
    Portfolio: define the broad ultimate target
            |
            v
    Study: receive recommendations, tune the exact setup, and apply it
            |
            v
    Audit -> Stage -> Run

Portfolio must never require a Study plan, Study size, case selection,
formulation, scenario configuration, or execution draft before its broad goal
can be applied.

Study must require one current applied Portfolio goal. Study then translates
that broad goal into a concrete recommendation. The scientist remains in
control of the final Study values. For example, if the applied Portfolio leads
to a recommendation of five paired runs, the scientist may choose six. The
final selected value, the original recommendation, and their difference must
all be visible and retained.

This plan does not change the direct Experiment > Individual experiment
contract. Individual execution remains independent of Workspace Portfolio and
Workspace Study.

3. VERIFIED CURRENT PROBLEM
===============================================================================

3.1 Immediate failure shown in the supplied screenshot

The detailed Portfolio status reports:

- retained submitted stage: CALO, TLBO, PSO, TSH-CALO;
- current editable experiment selection: CALO, TLBO, PSO.

That is algorithm-stage drift. Failing closed is correct because a Portfolio
cannot silently reinterpret an immutable submitted algorithm stage. The modal
summary is not correct or useful: "Review the selected evidence portfolio and
study size" hides the actual stage mismatch and incorrectly suggests that a
Study size is a Portfolio prerequisite.

Expected future presentation:

    Title: Portfolio goal was not applied
    Reason: Submitted algorithm stage no longer matches the Algorithms draft
    Retained stage: CALO, TLBO, PSO, TSH-CALO
    Current draft: CALO, TLBO, PSO
    Next action: Return to Algorithms, review the selection, and explicitly
                 Submit algorithms for experiment again.
    Safety statement: No Portfolio goal, Study setup, or execution plan changed.

Expected prerequisite or stage-drift states should be shown inline whenever
possible. Unexpected technical exceptions may still be recorded in Activity >
Logs, but expected prerequisite states must not be reduced to a generic error.

3.2 Structural ownership defect

Current Portfolio Apply performs responsibilities from two different layers:

- builds and validates PortfolioConfig;
- selects a Workspace algorithm subset;
- calls PortfolioPlanner.plan with current experiment/study values;
- derives required repetitions;
- writes the derived repetition count into ExperimentConfig.runs;
- writes reuse/resume execution values into ExperimentConfig;
- persists a Portfolio record;
- immediately creates a WorkspaceStudyPlan execution draft;
- emits Portfolio workflow completion.

The Study page then reads the Workspace draft that Portfolio created. This
makes Portfolio depend on concrete Study inputs while Study depends on a
Portfolio-created Study draft. The circular experience is therefore real even
where the command registry does not express it as a literal A->B->A cycle.

3.3 Duplicated study-planning authority

Study-strength and power-planning logic also exists in the retained Dashboard
compatibility implementation. The visible Workspace Study workflow separately
contains Case, Formulation, Budget + runs, Scenarios, Validate + outputs, and
Review + launch. A future implementation must establish one visible Study
authority and must not restore a second Dashboard study planner.

4. NON-NEGOTIABLE OWNERSHIP MODEL
===============================================================================

4.1 Algorithms authority

- Algorithms > Submit algorithms for experiment remains the only action that
  creates the immutable ordered algorithm stage.
- Portfolio may choose a non-empty comparison subset only from that stage.
- Portfolio never adds, removes, substitutes, qualifies, activates, or changes
  the parameters of a staged algorithm.
- A stage mismatch blocks Portfolio Apply with the exact identities and next
  action. It must never be described as a Study-size problem.

4.2 Portfolio authority: WHAT is the ultimate target?

Portfolio owns only broad, durable intent:

- Portfolio goal/type, such as diagnostic or repeated comparative evidence;
- desired evidence rigor/profile;
- intended article/output preset, if any;
- non-empty comparison scope selected from the submitted algorithm stage;
- requested figures, tables, and evidence outputs;
- storage/evidence class required by those outputs;
- independent-validation requirement;
- other publication/evidence requirements that describe the target rather
  than the experiment schedule.

Portfolio does not own:

- exact paired-run count;
- exact cases or case matrix;
- exact formulation cells;
- exact scenario family or contingency set;
- exact optimization budget, seed, workers, compute intent, result directory,
  reuse choice, resume choice, or checkpoint interval;
- a WorkspaceStudyPlan;
- fairness/audit receipts;
- execution-controller ownership.

4.3 Study authority: HOW will the Portfolio target be achieved?

Study consumes one exact applied Portfolio goal and owns:

- selected case or case matrix;
- ORPD formulation and variable/constraint setup;
- scenario/robustness design;
- paired runs selected by the scientist;
- population and exact evaluation budget;
- seed and deterministic pairing design;
- compute intent and result directory;
- exact-compatible-result reuse choice;
- resume/checkpoint behavior;
- concrete study cells and queue size;
- the immutable WorkspaceStudyPlan draft created only after Apply study setup.

4.4 Execution authority

- Audit, Stage, and Run remain separate explicit scientist actions.
- Applying a Portfolio goal or Study setup starts no numerical work.
- Only Stage may acquire the singleton Workspace controller.
- Workspace execution continues to use the existing shared ExperimentManager.
- The safe-pause, PAUSING versus PAUSED, resume, controller fencing, immutable
  evidence, exact FE accounting, and Individual handoff contracts remain
  unchanged.

5. PROPOSED PERSISTED ARTIFACTS
===============================================================================

5.1 AppliedPortfolioGoal

Introduce a versioned immutable Portfolio goal snapshot, conceptually:

    schema_version
    portfolio_goal_id
    created_at
    algorithm_stage_id
    algorithm_stage_sha256
    selected_algorithm_names
    selected_algorithm_parameter_sha256_by_name
    portfolio_type
    evidence_profile
    article_or_output_preset
    requested_outputs
    storage_or_evidence_class
    require_independent_validation
    intrinsic_requirements
    intrinsic_warnings
    content_sha256

Intrinsic requirements may include statements such as:

- at least N algorithms are required;
- CALO must be included for a requested CALO diagnostic;
- robust scenario evidence will be required in Study;
- at least N paired runs will be required;
- at least N benchmark blocks/cases will be required;
- particular stored result fields will be required.

These are constraints and recommendation inputs, not a concrete Study plan.

Applying a Portfolio goal persists this artifact and makes it the current
Portfolio goal. It must not create any execution_plan or workspace_plan_cell
record.

5.2 StudyRecommendation

Study computes a deterministic, read-only recommendation from:

- exact AppliedPortfolioGoal identity and SHA-256;
- exact submitted algorithm stage identity and SHA-256;
- current case/formulation/scenario capabilities;
- registered output requirements;
- existing power/effect-size planning rules;
- safe application defaults.

The recommendation should contain, conceptually:

    recommendation_schema_version
    portfolio_goal_id and SHA-256
    algorithm_stage_id and SHA-256
    hard_minimum_runs
    recommended_runs
    recommended_case_or_case_matrix
    minimum_benchmark_blocks
    recommended_formulation
    recommended_scenario_mode
    recommended_budget
    recommended_storage_fields
    recommended_validation_tasks
    default_reuse_and_resume_values
    explanation_by_field
    recommendation_sha256

Generating or refreshing a recommendation is read-only. It does not modify
ExperimentConfig, Portfolio, Study completion, audit state, or controller
ownership.

5.3 AppliedStudySetup and WorkspaceStudyPlan

When the scientist presses Apply study setup, persist:

- the exact recommendation identity and SHA-256;
- the scientist-selected values;
- a deterministic recommendation-versus-selection delta;
- every satisfied hard constraint;
- any permitted soft-recommendation deviation and its machine-generated
  warning classification;
- the exact Portfolio goal and algorithm-stage bindings;
- the concrete cells and queue count.

Only this action creates or replaces an unstarted WorkspaceStudyPlan draft.
Audit then binds to that exact immutable Study design.

8. RECOMMENDATION AND USER-OVERRIDE RULES
===============================================================================

Every tuneable recommended field should distinguish three concepts:

1. Hard minimum or compatibility boundary
   A value below this boundary cannot satisfy the applied Portfolio goal.

2. Recommended value
   The deterministic planner proposal based on the Portfolio target, study
   design, registered requirements, power assumptions, and safe defaults.

3. Scientist-selected value
   The editable value that will be frozen into the Study plan.

Example presentation:

    Paired runs
    Hard minimum: 3
    Recommended: 5
    Selected: 6
    Effect: +1 run per algorithm/case; target remains satisfied.

Rules:

- Increasing 5 to 6 is allowed and recorded.
- A selected value between a hard minimum and a higher soft recommendation is
  allowed with a visible machine-generated risk/deviation warning.
- A selected value below the hard minimum is blocked because the applied
  Portfolio target would no longer be satisfied.
- The UI must never silently increase or decrease the scientist-selected value
  during Apply.
- Recommendation hydration must use QSignalBlocker or equivalent so it cannot
  masquerade as a scientist edit or invalidate an audit.
- A user edit after an audit invalidates that audit immediately and truthfully.
- No superiority, sufficiency, statistical-power, publication, or release
  claim is inferred merely because a recommendation was accepted.

9. ONE-WAY STATE MODEL
===============================================================================

9.1 Portfolio states

PORTFOLIO_UNAPPLIED
    Editable goal draft; Study locked.

PORTFOLIO_APPLIED_CURRENT
    Immutable applied goal matches the submitted stage; Study enabled.

PORTFOLIO_EDITED_NOT_APPLIED
    Applied goal remains authoritative; edits are only a new working draft.
    Study continues to show which applied revision it uses.

PORTFOLIO_STALE_STAGE
    Submitted stage changed or no longer matches; Study locked for new work.

PORTFOLIO_LOCKED_BY_RETAINED_PLAN
    Bound Workspace plan is staged/running/pausing/paused/interrupted and must
    remain immutable. Portfolio remains inspectable but not replaceable.

9.2 Study states

STUDY_NO_PORTFOLIO
    Locked with the exact Apply Portfolio goal instruction.

STUDY_RECOMMENDATION_READY
    Recommendation is current; editable setup not yet applied.

STUDY_EDITED_NOT_APPLIED
    Controls differ from recommendation or last applied Study; no new plan.

STUDY_APPLIED_DRAFT
    Exact WorkspaceStudyPlan draft exists; audit required.

STUDY_AUDITED
    Exact draft has a passing audit receipt; Stage enabled.

STUDY_STAGED / RUNNING / PAUSING / PAUSED / INTERRUPTED_RESUMABLE
    Existing lifecycle/controller contracts apply.

STUDY_TERMINAL
    Completed, completed-with-failures, cancelled, failed-non-resumable, or
    discarded-unstarted according to existing lifecycle rules.

9.3 One-way invalidation

- Algorithm stage change invalidates Portfolio goal compatibility and all
  unstarted downstream Study recommendation/draft/audit state.
- Applying a new Portfolio goal revision invalidates only downstream Study
  recommendation/draft/audit state.
- Editing Study never invalidates or edits the applied Portfolio goal.
- Applying Study never rewrites Portfolio.
- Audit changes no Portfolio or Study design values.
- Stage freezes the exact applied Study and bound Portfolio identities.
- A Study error must never send the user back to Portfolio unless the exact
  applied Portfolio is missing, stale, or intrinsically incompatible.

There is no transition from Portfolio Apply to "Study already complete" and
no transition from Study Apply back into Portfolio mutation.
